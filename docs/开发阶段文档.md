# RAG 系统分阶段开发文档

本文将 [RAG架构.md](./RAG架构.md)、[RAG优化链路.md](./RAG优化链路.md)、[RAG缓存设计.md](./RAG缓存设计.md)、[RAG评估.md](./RAG评估.md) 和 [开发前的确定.md](./开发前的确定.md) 转换为可执行的开发计划。首期目标是可本地运行、可观测、可评估、支持个人和管理员两种角色的模块化单体 RAG 系统。

## 1. 首期范围和固定约束

首期使用 Python 3.10、FastAPI、SQLAlchemy 2.x、MySQL、Redis、OpenSearch 2.12.0 和 uv。OpenSearch 使用 IK 分词器，同时承担 BM25、k-NN 向量检索和元数据过滤。Dense 与 Sparse 由应用层并行调用，再使用 RRF 融合，不使用 OpenSearch Hybrid DSL。

固定配置：

- Embedding：千问 OpenAI-compatible API，向量维度 `1024`。
- 物理索引：`rag_chunks_v1`。
- 读 Alias：`rag_chunks_read`；写 Alias：`rag_chunks_write`。
- 开发默认值：`dense_k=5`、`sparse_k=5`、`final_top_k=5`。
- 首期文件：Markdown 和纯文本；PDF、Word 只实现解析器接口。
- 权限：`personal` 只能访问自己的资源，`admin` 可管理全部资源。
- 线上 Trace 保存脱敏后的完整答案，最多 10,000 字符，并受访问权限和保留周期控制。

每个阶段完成后必须通过该阶段验收，才能进入下一阶段。开发过程中如果需要改变固定约束，应先同步更新架构文档、Schema 和本文件。

## 3. 阶段 0：工程骨架和依赖验证

### 目标

建立前后端分离项目中的后端基础工程，并验证远程 MySQL、Redis、OpenSearch 以及 IK 插件连接。

### 交付物

- `backend/` Python 包和清晰的模块目录。
- `pyproject.toml`、`uv.lock`、`.env.example`。
- FastAPI 应用入口和健康检查接口。
- Docker 或服务器连接说明。
- 基础日志配置和统一异常入口。

建议模块边界：

```text
app/
  api/              # HTTP 路由和 DTO
  core/             # 配置、日志、安全、错误码
  db/               # SQLAlchemy、迁移、Repository
  models/           # ORM 模型
  schemas/          # Pydantic 请求、响应、SSE 模型
  services/         # 用例服务
  rag/              # 解析、切块、Embedding、检索、融合
  workers/          # 入库和清理任务
  observability/    # Trace、指标、审计
```

### 验收标准

- `uv run` 可以启动 FastAPI。
- `/health/live` 不依赖外部服务即可返回。
- `/health/ready` 能分别报告 MySQL、Redis、OpenSearch 状态。
- OpenSearch 能返回版本号，并确认 `analysis-ik` 已安装。
- 配置缺失时应用启动失败并给出明确变量名。

### 当前实现与验证记录

- 已完成 FastAPI 入口、配置、JSON 日志、请求 ID 中间件、统一错误响应、SQLAlchemy 异步引擎和健康检查。
- 已生成 `backend/uv.lock`，并使用 Python 3.10.20 执行 `uv sync --group dev`。
- `ruff check app tests` 通过；阶段 0 自动化测试 4 项通过；Python 3.10.20 下应用导入通过。
- `/health/live` 已返回 HTTP 200。
- `/health/ready` 已真实连接远程依赖并返回 HTTP 200：MySQL、Redis、OpenSearch 均正常；OpenSearch 版本为 2.12.0，`ik_smart` 和 `ik_max_word` 均可用。
- 阶段 0 代码和环境验收均已完成。IK 检查使用实际 `_analyze` 请求，不会静默退回 `standard` 分词器。

## 4. 阶段 1：配置、数据库和基础模型

### 目标

根据架构文档建立可迁移的 MySQL 模型，所有数据库连接 URL 从环境变量读取。

### 主要模型

- `user`：用户、角色、状态、密码哈希。
- `knowledge_bases`：知识库、所有者、当前发布版本。
- `documents`：逻辑文档、内容哈希、删除状态。
- `document_versions`：文件版本、解析器版本、切块策略版本。
- `ingestion_jobs`：入库状态机、重试次数、错误信息和租约。
- `query_traces`：线上和回放 Trace。
- `evaluation_dataset_snapshots`、`evaluation_dataset_cases`、`evaluation_runs`、`evaluation_case_results`：先完成表结构，评估逻辑后续实现。

### 关键约束

- 所有资源带 `owner_id` 或可追溯到知识库所有者。
- `knowledge_base_id + content_hash` 用于重复内容幂等判断。
- `document_version_id`、`chunk_id` 和 OpenSearch 文档 ID 可稳定重算。
- 任务领取使用数据库锁或租约，避免多个 Worker 重复处理。
- 状态、错误码和时间字段统一命名。

### 验收标准

- 数据库迁移可重复执行。
- 关键唯一索引和外键存在。
- 创建知识库、文档和任务的最小 Service 测试通过。
- 删除行为先标记主库状态，再产生异步清理任务。

### 当前实现与验证记录

- 已实现 11 个 SQLAlchemy 模型：用户、知识库、文档、文档版本、Chunk、入库任务、评估数据集快照、评估 Case、评估运行、评估 Case 结果和线上 Query Trace。
- 已建立 `backend/alembic/` 和初始迁移 `0001_initial`，所有连接配置从根目录 `.env` 的 `DATABASE_URL` 读取。
- ORM 映射、Ruff、阶段测试和 Alembic 离线 DDL 生成均通过。
- 远程数据库迁移命令已准备；执行 `uv run alembic upgrade head` 后，阶段 1 的远程数据库验收完成。

## 5. 阶段 2：认证、权限和知识库管理

### 目标

完成最小可用的用户登录、角色判断和资源隔离。

### 规则

- `personal`：只能读取和修改自己的知识库、文档和 Trace。
- `admin`：可以管理全部资源，但检索时仍必须明确指定知识库。
- MySQL Repository、OpenSearch Filter、Redis Key 三层都必须执行权限边界。
- 删除知识库先逻辑删除，再异步清理 Chunk。

### API 初版

- `POST /api/v1/auth/login`
- `POST /api/v1/knowledge-bases`
- `GET /api/v1/knowledge-bases`
- `DELETE /api/v1/knowledge-bases/{knowledge_base_id}`
- `GET /api/v1/documents`

### 验收标准

- 未登录请求返回统一认证错误。
- 用户 A 无法读取用户 B 的知识库和检索结果。
- 管理员可以查询指定知识库。
- 权限错误不会泄露资源是否存在的敏感信息。

### 当前实现与验证记录

- 已实现本地账号登录、Argon2id 密码哈希、短期 JWT Access Token、Token 过期校验和当前用户接口。
- 已实现 `personal` 与 `admin` 的知识库和文档查询边界：个人用户的 SQL 查询固定注入 `owner_id`，管理员可管理全部资源。
- 已实现知识库创建、列表、详情、软删除和文档列表接口；删除只更新 MySQL 状态，索引清理由后续异步任务处理。
- 已增加 `0002_kb_deleted_at` 迁移，为知识库软删除保存 `deleted_at`。
- 已完成权限查询单元测试和代码质量检查；认证依赖锁定及完整 API 集成测试需在 PyPI 访问恢复后执行 `uv sync`。

## 6. 阶段 3：文档解析、切块和入库任务

### 目标

实现 Markdown/TXT 的完整入库链路，PDF/Word 只保留统一接口。

### 处理流程

```text
上传文件
  -> 计算内容哈希
  -> 相同知识库和哈希则幂等返回
  -> 创建 documents/document_versions/ingestion_jobs
  -> PARSING
  -> CHUNKING
  -> EMBEDDING
  -> INDEXING
  -> READY
  -> 管理员发布后 PUBLISHED
```

异常状态进入 `RETRY_WAITING`，超过最大重试次数进入 `FAILED`。

### 设计要求

- `DocumentParser` 接口先实现 `MarkdownParser` 和 `TextParser`。
- `PdfParser`、`WordParser` 暂时只保留接口和未实现状态。
- Chunk ID 使用稳定规则，例如 `chunk_{document_version_id}_{序号}`。
- 重试时复用相同 Chunk ID，OpenSearch 使用 Bulk upsert 保证幂等。
- Embedding 请求批量化，返回数量和每个向量长度都必须校验为 `1024`。
- Chunk 元数据至少包含文档、知识库、所有者、版本、文件名、章节和语言。

### 验收标准

- Markdown 标题和正文可以被解析并切成可检索 Chunk。
- TXT 可以正常入库。
- 相同哈希重复上传不会产生新版本。
- Embedding 维度错误会使任务失败，不会写入 OpenSearch。
- 任务失败可重试，重试不会产生重复 Chunk。

## 7. 阶段 4：OpenSearch 索引和检索

### 目标

创建 `rag_chunks_v1` 和两个 Alias，验证 IK、BM25、k-NN 与过滤条件。

### Mapping 要求

- `title`、`content`：`text`，索引分析器 `ik_max_word`，搜索分析器 `ik_smart`。
- 向量字段：`knn_vector`，维度 `1024`。
- `owner_id`、`knowledge_base_id`、版本号和业务过滤字段：`keyword`。

### 查询实现

- `SparseRetriever`：关键词查询，`size=sparse_k`，使用默认 BM25。
- `DenseRetriever`：k-NN 查询，`k=dense_k`，附带相同权限和知识库过滤条件。
- 两路请求由应用层并行发送到 `rag_chunks_read`。
- 写入只访问 `rag_chunks_write`。

### 验收标准

- IK 分词效果通过中文关键词查询验证。
- 两路查询均能返回 Chunk ID、分数和元数据。
- 用户隔离过滤在两路查询中都生效。
- Alias 指向正确物理索引。
- 删除文档可以通过 Bulk 删除对应版本的全部 Chunk。

## 8. 阶段 5：并行检索、融合和缓存

### 目标

实现检索服务、RRF 融合、超时、熔断、降级和 Redis 缓存。

### 处理规则

- Dense 和 Sparse 使用独立超时，但共享请求总 Deadline。
- 任一路失败时保留另一条结果，并记录降级原因。
- 两路都失败时返回明确检索错误。
- RRF 结果截断到 `final_top_k`。
- 检索缓存 Key 必须包含所有影响权限和结果的版本、过滤条件及三个 K 值。
- 答案缓存首期默认关闭，评估回放必须关闭答案缓存。

### 验收标准

- 两路请求确实并行执行。
- 调整 `dense_k` 不会影响 `sparse_k`。
- Dense 单路故障、Sparse 单路故障和两路故障均有确定行为。
- 缓存命中不会跨用户泄露数据。
- 超时、熔断和降级信息进入 Trace。

## 9. 阶段 6：Chat 和 SSE

### 目标

完成基于检索上下文的 OpenAI-compatible Chat 调用，并通过 SSE 流式返回。

### SSE 协议

- `Content-Type: text/event-stream`。
- 每条事件以 `event:` 和 `data:` 开始，以 `\n\n` 结束。
- `seq` 从 1 递增。
- 事件：`start`、`delta`、`citation`、`heartbeat`、`end`、`error`。
- 一个请求只能以 `end` 或 `error` 结束。
- POST 请求首期使用 `fetch + ReadableStream`。

### 验收标准

- 前端可显示打字机效果。
- `start` 携带 `trace_id`。
- `citation` 能关联真实 Chunk。
- 生成中断可以发送 `error`。
- 首个有效增量和完整结束时间均被记录。

## 10. 阶段 7：Trace、错误码和可观测性

### 目标

让每次请求可以追溯配置、检索、生成、降级和最终结果。

### Trace 必须记录

```text
embedding_model
embedding_dimension
chunk_strategy_version
index_version
retrieval_version
dense_k
sparse_k
final_top_k
fusion_strategy
prompt_version
chat_model
timeout
degraded_reason
retrieved_chunk_ids
context_snapshot
citations
first_token_latency_ms
total_latency_ms
answer_text
```

`answer_text` 保存脱敏后的完整答案，最多 10,000 字符；超出时保存截断标记。原始 Prompt 和未脱敏输出不落库。

### 验收标准

- 所有 API 响应遵循统一结构。
- `request_id`、`trace_id`、异步任务和 SSE 可以关联。
- Trace 能区分 completed、degraded、failed。
- Trace 中能定位每个阶段的耗时和失败原因。
- PII 脱敏、长度限制和访问控制生效。

## 11. 阶段 8：评估和回归测试

### 目标

让评估链路真正消费线上 Trace，并能比较不同版本的检索和生成效果。

### 最小评估流程

```text
线上 Trace
  -> 选择 Trace 集合
  -> 固化 Dataset Snapshot
  -> 创建 run_manifest
  -> 执行评估
  -> 生成 evaluation_case_results
  -> 汇总检索、引用和答案指标
```

首期测试集至少覆盖：正常问答、无答案、权限隔离、引用错误、Dense 单路失败、Sparse 单路失败和模型超时。

### 验收标准

- 评估 Case 能引用具体线上 Trace。
- Dataset Snapshot 不会因原始数据后续变化而改变。
- `run_manifest` 能还原本次评估的模型、索引、Prompt、K 值和融合策略。
- 至少能输出 Recall@K、引用有效率、答案完整性和延迟。
- 可以比较两次不同配置的评估结果。

## 12. 阶段 9：稳定性和部署整理

### 目标

完成可重复部署、基础压测和故障恢复验证。

### 内容

- 完善 Docker Compose 或服务器部署说明。
- 增加数据库迁移、OpenSearch 初始化和 Alias 切换脚本。
- 验证 Worker 重启、任务重试和部分 Bulk 失败恢复。
- 验证 Redis 不可用时的降级行为。
- 验证 OpenSearch、Embedding、Chat 超时和熔断。
- 记录基础吞吐、P95 延迟和首 Token 延迟。

### 暂缓内容

多租户、复杂 RBAC、消息队列、Rerank、多向量字段、Agent、完整监控平台和大规模水平扩展，等核心链路稳定并完成评估后再引入。

## 13. 每个阶段的开发协作规则

每次实现一个阶段时，先确认对应文档和 Schema，再编写代码；完成后至少提供：

1. 修改的文件和模块。
2. 接口、数据表或配置的变化。
3. 验收命令和结果。
4. 未完成项和已知限制。
5. 对架构文档需要同步的内容。

任何会影响索引 mapping、向量维度、权限边界、Trace Schema 或 API 协议的改动，都必须同步更新设计文档和 Schema。
